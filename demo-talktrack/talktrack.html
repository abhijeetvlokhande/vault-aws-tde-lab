SQL Server TDE with HashiCorp Vault

Run this against the deployed lab from the companion repo. Every command below is copy-paste ready. Italic lines are what to say out loud — adapt them, don't read them verbatim.

Opening — set the frame

SAY

"Today I want to show you something running, not a slide. This is SQL Server's built-in encryption feature — Transparent Data Encryption — with the encryption key managed entirely by HashiCorp Vault instead of sitting on the SQL Server box. Everything you're about to see is a real environment we can poke at live."

Have the RDP session to the SQL Server box and an SSH terminal to the Vault box both already open before you start talking.

Act 1 — Can anyone actually read the data without the key?

SAY

"Encryption only matters if it actually stops someone from reading your data. Let's prove that directly, not just take the checkbox for granted. I've got two databases with the exact same customer data — one encrypted through Vault, one left unencrypted on purpose. I backed both of them up to a raw file. Let's search those files for a real customer's social security number."

RUN

PowerShell, on the SQL Server box

Write-Host "Unprotected backup:" -ForegroundColor Yellow
if (Select-String -Path "C:\Backups\BankDemo_Unprotected.bak" -Pattern "123-45-6789" -SimpleMatch -Quiet) {
    Write-Host "  MATCH FOUND -- customer SSN readable in raw backup file" -ForegroundColor Red
} else {
    Write-Host "  No match found" -ForegroundColor Green
}

Write-Host "`nVault-encrypted backup:" -ForegroundColor Yellow
if (Select-String -Path "C:\Backups\TestTDE.bak" -Pattern "123-45-6789" -SimpleMatch -Quiet) {
    Write-Host "  MATCH FOUND" -ForegroundColor Red
} else {
    Write-Host "  No match found -- data unreadable without the Vault-managed key" -ForegroundColor Green
}

Expect: red "MATCH FOUND" for the unprotected backup, green "No match found" for the Vault-encrypted one.

SAY

"That's the whole point in one screen. Same data, same schema, one line of difference in how the database was set up — and one of these files is just readable text sitting on disk, and the other genuinely isn't, because the key that would unlock it lives in Vault, not next to the data."

Act 2 — What happens if Vault goes down?

SAY

"The honest question anyone should ask about this design is: what happens if Vault isn't reachable? Does the database fall over badly, or does it fail safely? Let's find out for real — I'm going to stop Vault right now."

RUN

SSH, on the Vault box

sudo systemctl stop vault
RUN

SSMS, on the SQL Server box

ALTER DATABASE TestTDE SET OFFLINE;
GO
ALTER DATABASE TestTDE SET ONLINE;
GO

Expect: this fails. That's supposed to happen.

SAY

"Good — it just failed. That's not a bug, that's the proof. The key genuinely isn't cached anywhere useful on the SQL Server box. It's only in Vault. Now let's bring Vault back and show that recovery is clean, not a disaster."

RUN

SSH, on the Vault box

sudo systemctl start vault
export VAULT_ADDR=http://127.0.0.1:8200
vault operator unseal $(jq -r '.unseal_keys_b64[0]' /home/ubuntu/vault-init.json)
vault status

Wait for HA Mode: active before moving on.

RUN

SSMS, on the SQL Server box

ALTER DATABASE TestTDE SET ONLINE;
GO

Expect: this succeeds now.

SAY

"And that's the recovery path — unseal Vault, confirm it's active, and the database comes right back. No SQL Server restart needed. That's a real, tested answer, not a guess from a docs page."

Act 3 — Key rotation, on both sides

SAY

"Security teams rotate keys on a schedule. Two different rotations matter here — rotating the database's own key, and rotating the master key sitting in Vault. Let's do the Vault-side one, because it answers the scariest version of the question: if I rotate the master key, does my running database break?"

RUN

SSH, on the Vault box

vault write -f transit/keys/ekm-encryption-key/rotate
vault read transit/keys/ekm-encryption-key
RUN

SSMS — without touching SQL Server at all

SELECT TOP 5 * FROM TestTDE.dbo.Customers;

Expect: data comes back with no error, no interruption.

SAY

"Nothing broke. Vault kept the old key version valid, so rotating the master key doesn't force an outage — it gives us a grace period to re-wrap the database's key on our own schedule, whenever we choose to."

Performance — does this slow anything down?

SAY

"Last question people ask: does routing the key through Vault make the database slower? We measured this two ways instead of guessing."

SHOW

Vault is only called once, when the database comes online — this measures that one moment, five separate times.

"Vault adds roughly eighty milliseconds — a one-time cost, only when the database starts up. That's the entire cost."

SHOW

Same test, scaled up to 100,000 rows — the two lines stay on top of each other.

"And here's 100,000 rows inserted, encrypted and unencrypted, side by side. They track within about two percent of each other at every scale we tested. Once the database is online, the key is already unwrapped and sitting in memory — Vault genuinely isn't involved in a single query after that."

Anticipated questions

"What if we need this on Standard edition, not Enterprise?"
TDE's key management feature only exists on SQL Server Enterprise or Developer edition — that's a Microsoft licensing boundary, not a Vault limitation. There's no workaround.
"Does this need a special network path opened up?"
Just one port, from the SQL Server host to Vault's API port. No new protocol, no separate listener beyond what Vault already uses.
"What's the actual failure mode we should plan operational runbooks around?"
A Vault outage means the database can't come back online until Vault is reachable again — walk through Act 2 again if this comes up live. It fails safely, but it is a real dependency your ops team needs to know about.
"Is this the same thing as KMIP?"
No — this lab uses Vault's own native EKM provider talking to Vault's Transit engine directly. KMIP is a different, separate integration path with its own setup, not covered in this lab.
